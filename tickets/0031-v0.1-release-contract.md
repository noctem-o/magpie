# Ticket 0031: Magpie v0.1.0 release contract

## Goal

Define the exact semantic boundary intended for Magpie `v0.1.0` without
changing code, versions, manifests, policy, canonical bytes, CI, or runtime
behaviour.

The landed contract lets a later packaging/tag PR act mechanically: a reviewer
can identify every promise, find committed evidence for it, and distinguish it
from capabilities Magpie does not possess.

## Architectural law

```text
v0.1.0 names a precise verified capability boundary.

It promises only behaviours backed by committed formats, explicit policy
identities, deterministic replay, hostile tests, and executable
demonstrations.

It does not imply production readiness, general truth resolution,
crates.io publication, or stable pre-1.0 Rust APIs.
```

## Why this boundary is needed now

The first complete governed-standing vertical slice is landed: verified L0
history, typed candidate material, policy v0 explanation, one exact
snapshot-only policy v1 result, hostile controls, contribution-lane discipline,
and byte-identical drop-and-replay through the public tour. Without an explicit
release contract, a `v0.1.0` tag could be misread as promising general standing,
production operation, packaging, or stable Rust APIs that do not exist.

The repository is private. The immediate release meaning is an internally
tagged, reproducible source boundary whose claims are fully stated and
independently reviewable. This ticket does not create that tag.

## Included capabilities

The contract records only behaviour implemented and tested on starting commit
`9329fa952d4bf9485f4bf2b3e51235a5377c095d`:

- L0 signed append-only history, hash chaining, automatic genesis, externally
  supplied trust root, `magpie-core-v1`, `magpie-sig-v1`, golden vectors,
  verify-before-apply replay, and independent Python verification;
- portable deterministic projections: compatibility `ClaimsView`, typed
  `StandingView`, co-replayed `StandingReplaySnapshot`,
  `DeadboltAnchorIndex`, and SQLite/FTS5 `EpisodicView`;
- typed claims, evidence, and justification edges with closed vocabulary,
  exact scope matching, deterministic graph replay, and legacy-status
  quarantine;
- policy `magpie-claims-standing-v0`: fail-closed candidate explanation,
  support/refutation ceilings, support-context requirements, stable trace and
  blocker output, and no achieved promotion;
- policy `magpie-claims-standing-v1`: one exact
  `DeadboltAnchor × Occurrence/Inclusion` direct-proof rule over a five-field
  identity co-replayed in the same verified snapshot;
- zero-or-one closed contribution-lane classification, exhaustive dispatch,
  replayed-node revalidation, and no counting or amplification;
- the public governed-standing tour with positive occurrence, one-field
  mismatch, interpretation control, complete verification, exact blocker
  ordering, and byte-identical replay.

## Exact exclusions

The contract prominently excludes:

- a general truth oracle and general achieved `Supported`, `Settled`, or
  `Refuted`;
- ordinary writer admission, `EpistemicGate`, MCP writes, or an ordinary CLI
  writer;
- deterministic-verifier settlement beyond the one Deadbolt occurrence rule;
- aggregation, refutation application, independence amplification, source
  counting, quorum, scoring, probability, or corroboration thresholds;
- contradiction debt, invalidation, supersession, and currentness/freshness
  semantics;
- ambient latest-policy selection, policy negotiation, fingerprints, or
  persisted bundles;
- foreign Deadbolt bundle-content verification;
- production key custody, concurrency, operational security, hosting,
  packaging, or deployment guarantees;
- librarian/navigator, model/lens ingestion, graph traversal, vector retrieval,
  reranking, and evaluator infrastructure;
- crates.io publication, stable pre-1.0 Rust APIs, or arbitrary future-policy
  compatibility.

These are absent from `v0.1.0`; absence does not by itself prohibit later work.

## Stability classification

The contract separates:

- **frozen:** `magpie-core-v1`, genesis semantics, and the signature domain;
- **byte-pinned/immutable:** existing payload encodings and golden vectors;
- **conditionally additive:** fresh payload tags only under documented format
  evolution with all old bytes unchanged;
- **protocol-defined:** the optional Deadbolt anchor seam and its exact
  verification split;
- **policy-ID pinned:** v0 candidate semantics and the one-rule v1 semantics;
- **release-pinned derived bytes:** representative v0/v1 resolution fixtures,
  explicitly not L0 encoding;
- **policy-v1 implementation law:** closed zero-or-one contribution lanes with
  no bypass or amplification;
- **deterministic comparison surfaces:** other named derived canonical bytes,
  without claiming they are persistent protocols;
- **pre-1.0 unstable:** public Rust APIs;
- **not yet prepared/not promised:** crate versions, package metadata,
  crates.io publication, and production operational security.

## Evidence requirements

`docs/releases/v0.1.0-contract.md` maps claims to concrete evidence and failure
modes, including:

- `docs/FORMAT.md`, golden tests/fixture, chain hostile tests, and the
  independent Python verifier for L0;
- changing-store and valid-prefix hostile tests for verified-before-replayed
  atomicity;
- claim, standing-snapshot, and episodic regeneration tests;
- standing-resolution fail-closed and exact v0-byte tests;
- snapshot provenance and verification-failure tests;
- all v1 context outcomes, five-field mismatch coverage, authority-confusion
  rejection, non-veto behaviour, duplicate/multi-path non-amplification,
  interpretation non-settlement, and literal v1 bytes;
- the CI-executed governed tour and both independent fixture commands.

The contract distinguishes current CI commands, repository tests, and later
tag-readiness checks. It does not claim that the portable fixture verifier or
`cargo package` currently runs in CI.

## Acceptance criteria

- The contract states the intended `v0.1.0` status and private-repository
  release meaning without claiming a tag or GitHub release exists.
- The release thesis and all four authority distinctions are explicit.
- Included capabilities match only implemented and tested behaviour.
- Absent capabilities are prominent and comprehensive.
- Stability separates format, policy, derived bytes, Rust APIs, crate versions,
  and operational posture.
- Every meaningful promise maps to committed evidence and a failure mode.
- Trust-root assumptions, sole legitimate construction paths, and manual
  bypasses are explicit.
- Format, policy, Rust API, and repository release versioning are distinct.
- The future acceptance checklist contains no publication command.
- Only the three scoped documentation files change.
- Required validation passes.
