# Ticket 0032: Magpie v0.1.0 non-publishable release metadata

## Goal

Coordinate explicitly non-publishable metadata for all three crates, make
their selected source inventories deterministic and reviewable, and verify
`magpie-log` as the only standalone archive promised by this phase.

Starting commit: `626f633afdd106acbfd6bb404d3b1493939927c7`.

## Architectural law

```text
Artifact inspection is not publication authority.

Release metadata must accurately describe the current source boundary
without inventing registry availability for unpublished internal crates.

A path-only internal dependency is more honest than a normalized
registry dependency that cannot exist under the chosen non-publication
posture.
```

## Exploratory blocker and corrected boundary

The prior clean exploratory run established:

```text
cargo package --workspace --locked --no-verify
cannot assemble dependent Magpie packages while their normalized
magpie-log dependency points to a registry version that does not exist.

--no-verify skips extracted-package compilation; it does not bypass
package preparation or registry resolution.
```

The correction is to narrow the claim, not fabricate registry availability.
All three inventories are checked. `magpie-log` is assembled and verified.
The dependent crates remain path-workspace packages and have no independent
archive guarantee.

## Landed metadata and licensing

- `[workspace.package]` owns version `0.0.1`, edition `2021`, the existing
  `MIT OR Apache-2.0` expression, repository, shared README, and
  `publish = false`.
- Every member inherits those six common fields and retains its crate-specific
  name and description.
- `magpie-claims` and `magpie-episodic` retain the exact path-only
  `magpie-log = { path = "../magpie-log" }` dependency. No internal version or
  workspace dependency entry is added.
- Standard Apache-2.0 and MIT texts are added at the workspace root. The MIT
  attribution is `Copyright (c) 2026 Magpie contributors`.
- Each crate contains byte-identical package-local license copies because
  Cargo does not select the workspace-root licenses for member inventories.
- Cargo does select the inherited root README, so no local README copies or
  include/exclude lists are added.

## Inventory and archive guarantees

Every member inventory contains its normalized/original manifests, generated
lockfile, README, both licenses, source, tests, applicable examples, and
required fixtures, while excluding repository administration, tickets,
credentials, unrelated crates, build output, and archives.

`magpie-log` passes full `cargo package -p magpie-log --locked` verification.
Its archive is inspected for version, non-publication posture, normalized
metadata, selected contents, and Cargo VCS metadata. The dependent packages
remain covered by workspace Clippy/tests and inventory inspection, not an
independent archive claim.

## CI checks

`tools/check_release_metadata.py` uses only Python's standard library to:

- validate all three Cargo metadata records;
- enforce version `0.0.1` and `publish = false`;
- validate repository, README, edition, license, and path-only dependencies;
- compare package-local license bytes with the roots;
- list all three inventories and require shared/package-specific files;
- reject obvious prohibited paths.

CI runs that checker after workspace tests and the governed tour, then runs a
separate `cargo package -p magpie-log --locked` step.

## Files in scope

## Explicit non-goals

No Rust source/test/example change; no runtime, API, policy, canonical,
fixture, verifier, dependency-version, feature, MSRV, changelog, version bump,
registry, publication, tag, GitHub release, artifact upload, or full-workspace
package-assembly change.

## Acceptance and validation

- All crates remain `0.0.1` and explicitly non-publishable.
- Shared metadata is inherited without centralizing descriptions.
- Internal dependencies remain path-only.
- License copies are byte-identical and all inventories contain README and
  both license texts.
- Metadata/inventory checks, formatting, strict Clippy, workspace tests, the
  governed tour, standalone `magpie-log` packaging, and both independent
  verifiers pass.
- The archive and normalized manifest are inspected, `Cargo.lock` remains
  byte-identical, and frozen surfaces remain unchanged.

## Follow-up boundary

Later human-controlled work must create the changelog and coordinated `0.1.0`
version bump, re-run the release acceptance checklist, and explicitly create
the tag and any GitHub release. Any registry publication decision additionally
requires version-plus-path internal dependency metadata, dependency-order
publication or another chosen registry, and a separate reviewed contract.
