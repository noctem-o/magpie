# Ticket 0033: Magpie v0.1.0 release candidate

## Goal

Create the initial changelog and coordinate the inherited workspace version
from `0.0.1` to `0.1.0` without creating a tag, GitHub release, registry
publication, or semantic capability.

Starting commit: `2ef3b8c7896211d734deb9c5f58b6344773bd2d1`.

This PR prepares the exact source candidate but does not decide that
the candidate has been released.

Only the human-created `v0.1.0` tag names the released commit.

## Architectural law

```text
A version identifies prepared source.
A tag identifies the exact released commit.

Changing Cargo metadata to 0.1.0 does not itself create a release,
publication authority, registry availability, or a new epistemic claim.

The changelog summarizes only capabilities already admitted by the
v0.1.0 release contract.
```

## Exact scope

- Add `CHANGELOG.md` and this ticket.
- Change the one root workspace version to `0.1.0`.
- Regenerate only the three local package versions in `Cargo.lock`.
- Pin the release metadata checker independently to `0.1.0`.
- Update current-state wording in README and the two release documents.
- Leave member manifests, CI, licenses, Rust, fixtures, verifier, format,
  policy, and dependencies unchanged.

## Changelog doctrine

The `2026-07-12` entry records the prepared source milestone, not an existing
tag. It summarizes the signed L0, frozen format and signatures, verified
replay, deterministic projections, typed governed vocabulary, policy-v0
candidate explanation, the one exact policy-v1 occurrence rule,
non-amplifying contribution lanes, governed tour, regeneration proof, and
non-publishable release metadata.

It prominently excludes general truth resolution, general achieved standing,
aggregation, contradiction debt, invalidation, supersession, currentness,
admission/writers, foreign bundle verification, production guarantees,
future model/retrieval/navigation infrastructure, stable Rust APIs,
publication, and independently registry-resolvable dependent crates.

Crate semver remains separate from `magpie-core-v1` and the fixed
`magpie-claims-standing-v0` / `magpie-claims-standing-v1` policy identities.

## Coordinated version and lockfile

All members continue to use `version.workspace = true`; no literal member
version is added. Cargo regenerates exactly these local lockfile fields:

```text
magpie-claims   0.0.1 -> 0.1.0
magpie-episodic 0.0.1 -> 0.1.0
magpie-log      0.0.1 -> 0.1.0
```

No registry version, checksum, source, dependency list, feature, or lockfile
format changes. Both internal dependencies remain exactly
`magpie-log = { path = "../magpie-log" }`.

## Metadata checker

`tools/check_release_metadata.py` defines `EXPECTED_VERSION = "0.1.0"` and
uses it as an independent release-candidate assertion. It continues to enforce
exactly three packages, `publish = false`, repository, license, edition,
inherited README, path-only internal dependencies, byte-identical licenses,
required inventory contents, and prohibited paths.

## Current and historical version references

Current-state `0.0.1` references in the root manifest/lockfile, checker,
README, release contract, and release-metadata document become `0.1.0`.
Ticket 0032 intentionally retains `0.0.1` because it records the earlier
metadata-preparation phase. Ticket 0031 remains an earlier contract record.

## Documentation changes

The release contract records the versioned source candidate, adds exact
version/checker/changelog/tag-absence acceptance checks, and preserves all
semantic boundaries. The release-metadata document and README link the
changelog, record `0.1.0`, and keep the non-publication, path-workspace,
standalone-`magpie-log`, and human tag-authority boundaries explicit.

## Explicit non-goals

No tag, GitHub release, crates.io publication, registry action, independent
dependent package archive, MSRV, dependency update, CI change, Rust/API
change, epistemic capability, format/policy identity change, fixture change,
verifier change, license change, artifact commit, or artifact upload.

## Acceptance criteria and validation

- Exactly three workspace packages resolve to `0.1.0` and remain explicitly
  non-publishable.
- Exactly three local lockfile version fields change.
- The checker, all three inventories, and standalone
  `magpie-log-0.1.0.crate` verification pass.
- Formatting, strict Clippy, workspace tests, governed tour, and both
  independent verifiers pass.
- Version/publication searches are reviewed; frozen surfaces are unchanged.
- `v0.1.0` and GitHub releases remain absent.

## Remaining human-controlled tag procedure

After merge, a human must update clean `main`, confirm this candidate commit is
the intended release source, run the complete acceptance checklist, review the
changelog and all absence boundaries, confirm no blocking PR remains, and
verify `v0.1.0` is still absent. Only then may the human create the annotated
`v0.1.0` tag at that exact commit, push it, and separately decide whether to
create a GitHub release. Registry publication remains outside that procedure.
