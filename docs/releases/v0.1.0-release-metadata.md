# Magpie v0.1.0 Release Metadata

## Status and policy

The coordinated workspace version is now `0.1.0`, preparing an exact source
candidate without creating a release. Every crate remains explicitly
non-publishable. Only `magpie-log` retains the standalone archive guarantee;
the dependent crates remain path-workspace packages. The `v0.1.0` tag and any
GitHub release are still absent.

Architectural law:

```text
Artifact inspection is not publication authority.

Release metadata must accurately describe the current source boundary
without inventing registry availability for unpublished internal crates.

A path-only internal dependency is more honest than a normalized
registry dependency that cannot exist under the chosen non-publication
posture.
```

A successful `cargo package --list` proves the selected source inventory.
It does not prove that every normalized dependency is registry-resolvable.

The `magpie-log` `.crate` is an inspectable source artifact.
It is not the Magpie `v0.1.0` release and grants no publication authority.

## Corrected package posture

The workspace shares version, edition, license expression, repository,
README, and `publish = false` through `[workspace.package]`. Each member
inherits those fields while retaining its own name, description, dependency
set, and features. No MSRV, authors, homepage, documentation URL, keywords,
categories, badges, or registry-specific metadata is introduced.

`magpie-claims` and `magpie-episodic` deliberately retain:

```toml
magpie-log = { path = "../magpie-log" }
```

That declaration says the crates are members of this source workspace. It
does not promise a registry fallback. The coordinated source version is now
`0.1.0`; a future publication decision would still need reviewed
version-plus-path dependency metadata, dependency-order publication or another
explicitly selected registry, and a separate contract. It may also require a
separate coordinated version decision; this source-candidate bump grants no
registry authority.

## Cargo boundary discovered during exploration

```text
cargo package --workspace --locked --no-verify
cannot assemble dependent Magpie packages while their normalized
magpie-log dependency points to a registry version that does not exist.

--no-verify skips extracted-package compilation; it does not bypass
package preparation or registry resolution.
```

Publication, a fabricated local/private registry, Git dependencies,
`[patch.crates-io]`, source replacement, vendoring, dummy packages, and
credentials are not acceptable workarounds. The package claim is narrowed
instead: all inventories are checked, while only `magpie-log` is assembled and
verified as a standalone archive.

## README and licenses

Cargo includes the inherited workspace `README.md` in every member inventory,
so package-local README copies are unnecessary. The declared dual license is
implemented by standard `LICENSE-APACHE` and `LICENSE-MIT` texts. The MIT text
uses `Copyright (c) 2026 Magpie contributors` because no canonical alternative
holder is recorded.

Cargo does not automatically include the workspace-root license files in each
member inventory. Each crate therefore has package-local `LICENSE-APACHE` and
`LICENSE-MIT` copies, checked byte-for-byte against the root files.

## Deterministic inventories

The checked inventories contain normalized and original manifests, generated
package lockfiles, the shared README, both license texts, and only the relevant
crate sources, tests, examples, and fixtures:

- `magpie-log`: library sources, `regen_golden`, chain/golden/portable-anchor
  tests, and `testdata/golden-v1.jsonl`;
- `magpie-claims`: library sources, the governed tour, and its projection,
  standing, occurrence, snapshot, and portable-anchor tests;
- `magpie-episodic`: library source and the episodic integration test.

The inventories exclude repository administration, tickets, other workspace
crates, credentials, environment files, editor state, logs, `target`, and
generated archives. No `include` or `exclude` arrays are needed.

## Verification boundary

CI and release validation run metadata checks and all three inventory listings.
They also compare local licenses to the roots and reject obvious prohibited
inventory paths. `cargo package -p magpie-log --locked` assembles and verifies
the only crate without an internal Magpie dependency; its archive contains the
expected `0.1.0` metadata, README, licenses, sources, example, tests, and
golden fixture.

The `.cargo_vcs_info.json` entry identifies the source Git commit as Cargo
metadata. It is not cryptographic provenance and does not replace Magpie's
signed-log trust model.

The dependent crates remain workspace-buildable path packages. They are not
described as independently packageable or registry-resolvable, and no full
workspace archive command is an acceptance requirement.

## Versioned source candidate and deferred release authority

The coordinated version bump and initial [`CHANGELOG.md`](../../CHANGELOG.md)
now prepare the source candidate. They create no tag, GitHub release, or
publication. After this candidate PR is merged, a human must re-run the release
contract checklist against clean `main`, review the exact commit, and only then
decide whether to create the `v0.1.0` tag and any GitHub release. Registry
publication would require its own separate decision and contract.
