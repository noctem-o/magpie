# Magpie v0.1.0 Release Contract

## 1. Status

This document defines the intended `v0.1.0` contract. It freezes the meaning
of the milestone, not the entire pre-1.0 implementation.

As of the contract preflight on 2026-07-12, the intended `v0.1.0` tag has not
been created. The repository has the earlier, format-specific
`magpie-v1-format-freeze` tag and no GitHub releases; neither is a `v0.1.0`
release. This contract does not create a tag or GitHub release.

`v0.1.0` is intended to be a **source, format, policy, replay, and
architectural milestone**. Because the repository is currently private, its
immediate release meaning is:

> an internally tagged, reproducible source boundary whose claims are fully
> stated and independently reviewable

Package preparation, crate version changes, changelog creation, tagging, and
any GitHub release are separate later actions. A later tag must identify a
commit that satisfies this contract. Unmerged or planned work is not part of
`v0.1.0`.

Architectural law:

> v0.1.0 names a precise verified capability boundary. It promises only
> behaviours backed by committed formats, explicit policy identities,
> deterministic replay, hostile tests, and executable demonstrations. It does
> not imply production readiness, general truth resolution, crates.io
> publication, or stable pre-1.0 Rust APIs.

## 2. Release thesis

The narrow vertical thesis is:

> One signed append-only history is completely verified before replay. Typed
> claim material remains candidate-only under policy v0. One exact Deadbolt
> occurrence proposition may earn `Settled` under explicit snapshot-only
> policy v1. Structured mismatch and interpretation controls remain
> unpromoted. All derived snapshots and resolutions regenerate
> byte-identically.

Four distinctions bound every promise in this contract:

```text
stored information != justified belief
ceiling != achieved standing
occurrence != interpretation
candidate != contribution
```

## 3. Included capabilities

### L0 signed log

`magpie-log` provides the authoritative L0 record:

- a signed, append-only event history with no update or delete operation;
- SHA-256 content hashes and a `prev_hash` chain with exact sequence checks;
- automatic `Genesis` at sequence 0 when `LogWriter` opens an empty store;
- a genesis record that declares `magpie-core-v1` and the verifying key, while
  trust in that key remains external;
- Ed25519 signatures over the domain-separated message
  `magpie-sig-v1 || content_hash`;
- the frozen `magpie-core-v1` canonical encoding: fixed field order,
  big-endian integers, length-prefixed exact UTF-8, and tagged payloads;
- JSON-lines physical storage kept distinct from canonical hash and signature
  preimages;
- one-read, verify-before-apply replay: an entire stored record snapshot is
  parsed and verified before any event is applied to a projection;
- `LogWriter` as the explicit write capability and `LogReader` as the
  read-only surface; `LogReader::events()` is explicitly unverified and is not
  a trusted projection origin;
- committed golden hashes, signatures, canonical preimages, and fixture bytes;
- an independent Python verifier implemented from `docs/FORMAT.md`.

This is history integrity relative to a supplied trust root. It is not a claim
of production key custody or operational security.

### Portable and derived projections

The portable base runs without Deadbolt and derives state by deterministic
folds over verified replay:

- `ClaimsView` is the compatibility projection for legacy claim/status events.
  Its `canonical_bytes()` surface is deterministic JSON and is tested for
  drop-and-replay equality.
- `StandingView` retains typed claims, evidence, and justification edges,
  quarantines legacy raw standing, and exposes deterministic v0 resolution.
  Its own canonical bytes and v0 resolution bytes are deterministic derived
  surfaces.
- `StandingReplaySnapshot` co-replays `StandingView` and
  `DeadboltAnchorIndex` from one completely verified event snapshot. Its
  `canonical_bytes()` includes the component bytes and verified event count.
- `DeadboltAnchorIndex` retains exact five-field identities and ordered
  occurrences, including sequence, event hash, and provenance. Its canonical
  bytes are deterministic derived audit bytes.
- `EpisodicView` is a SQLite/FTS5 projection. SQLite files and page layout are
  not authoritative or canonical; `EpisodicView::canonical_bytes()` serializes
  the derived rows ordered by sequence for rebuild comparison.
- Derived state may be destroyed and regenerated from the log. Tests cover
  compatibility-claim regeneration, standing/anchor snapshot regeneration,
  v0/v1 resolution regeneration, and episodic live-build versus rebuild
  equality.

Only the named `canonical_bytes()` comparison surfaces are byte-compared.
SQLite database bytes and presentation stdout are not stable serialization
contracts.

### Governed claim vocabulary

The additive L0 vocabulary includes:

- typed `ClaimAssertedV2` claim nodes;
- typed `EvidenceRegistered` evidence nodes;
- typed `JustificationEdgeRecorded` graph edges;
- closed evidence kinds and actor classes at the L0 boundary;
- seven closed claim domains parsed by standing policy from `metadata_json`;
- exact, opaque `scope_ref` matching with no prefix, containment, wildcard,
  inheritance, lattice, or ontology semantics;
- deterministic replay of claim, evidence, and edge tables;
- legacy raw standing retained as quarantined audit material rather than
  governed truth.

Vocabulary presence grants no authority. Labels, actor classes, metadata,
content hashes, and prose remain asserted data until an explicit resolver
uses replay-derived context.

### Policy v0

The exact policy identifier is `magpie-claims-standing-v0`.

Policy v0 provides:

- a fail-closed `StandingResolution` explanation for a target claim;
- closed support ceilings by `EvidenceKind × ClaimDomain`;
- separate closed refutation ceilings;
- support-context requirements distinguishing no contribution, no privileged
  context, human admission, deterministic verifier context, and Deadbolt
  verifier context;
- deterministic trace and blocker output, including stable ordering;
- rejection or explicit blockers for malformed metadata, unknown domains or
  evidence kinds, missing graph endpoints, unsupported edge kinds, and scope
  mismatch;
- quarantine of legacy raw status;
- no achieved promotion: candidate ceilings remain maxima, not achieved
  standing;
- preservation of `StandingView::resolved_standing()` as the compatibility v0
  scalar.

For the release fixture, policy v0 remains `Conjectured` even when the
candidate ceiling is `Settled`.

### Policy v1

The exact policy identifier is `magpie-claims-standing-v1`.

Policy v1 is available only through the explicit snapshot methods
`StandingReplaySnapshot::resolved_standing_v1` and
`StandingReplaySnapshot::resolved_standing_with_trace_v1`. It has one
achieved-standing rule:

```text
supports edge
× exact evidence/edge/target scope
× DeadboltAnchor
× Occurrence/Inclusion
× exact segment_anchored_v1 claim predicate
× exact segment_anchored_v1 evidence reference
× exact five-field identity in the same StandingReplaySnapshot anchor index
× Matched
→ direct contribution Settled
→ governed standing Settled
```

The five identity fields are `bundle_kind`, `witness_root`,
`witness_algorithm`, foreign `canonicalization_profile`, and `run_id`. The
claim predicate, evidence reference, and replayed anchor must agree exactly.
The resolver re-fetches and revalidates the replayed edge, target, and evidence
instead of trusting a caller-created candidate trace.

`Matched` is the sole successful context result and contributes exactly
`Settled`. The audit trace retains the matched identity, earliest sequence,
event hash, and provenance. Structured failures distinguish wrong kind, wrong
domain, missing or malformed claim predicate, missing or malformed evidence
reference, predicate/reference mismatch, and absent anchor. An unrelated
blocked path does not veto a matched direct proof. Duplicate anchors and
multiple successful paths do not amplify standing; the earliest duplicate
occurrence is retained deterministically.

This rule settles only the proposition that the exact identity occurs in the
accepted chain. It is not general settlement and does not verify or interpret
the foreign bundle.

### Contribution lanes

Policy v1 classifies each v0 candidate into deterministically zero or one
closed contribution lane. `StandingPolicyRule` is the serialized lane identity
and currently has only `DeadboltOccurrenceInclusionV1`. Dispatch is exhaustive,
with no wildcard arm.

Lane selection contributes nothing by itself. The selected lane revalidates
replayed material and may produce one bounded direct contribution or none.
Lane count is audit material: it creates no counting, scoring, voting,
threshold, confidence, corroboration, or amplification behaviour. The lane
refactor preserves the pre-lane v1 result, serialized shapes, exact
representative bytes, trace order, blocker order, occurrence identity,
sequence, event hash, and provenance.

### Executable public demonstration

`crates/magpie-claims/examples/tour.rs` is the executable governed-standing
tour. It demonstrates:

- complete chain verification before governed replay;
- one co-replayed standing/anchor snapshot;
- a positive exact occurrence path: v0 `Conjectured`, explicit v1 `Settled`;
- a one-field `run_id` mismatch with exact
  `PredicateReferenceMismatch` and no contribution;
- an `Interpretation` control over the same anchor that remains
  `Conjectured` with no v1 application;
- exact candidate reason and blocker ordering;
- retained matched audit material;
- dropping all derived standing state, replaying from signed history, and
  obtaining identical typed facts, snapshot bytes, and all six v0/v1
  resolution byte surfaces.

CI runs the exact command:

```text
cargo run --locked --example tour -p magpie-claims
```

The assertions are the demonstration contract. Its stdout transcript is not
pinned.

## 4. Explicitly absent capabilities

`v0.1.0` deliberately does **not** provide:

- a general truth oracle or general-purpose truth engine;
- ordinary writer-facing admission or `EpistemicGate`;
- general achieved `Supported`, general achieved `Settled`, or achieved
  `Refuted`;
- deterministic-verifier achieved-standing lanes beyond the exact Deadbolt
  occurrence rule;
- support aggregation, refutation application, independence amplification,
  source counting, quorum logic, confidence scoring, or probabilistic belief;
- contradiction debt, invalidation semantics, supersession semantics, or
  currentness/freshness policy;
- ambient latest-policy selection, runtime policy negotiation, policy
  fingerprints, or persisted policy bundles;
- verification of foreign Deadbolt bundle contents by their native verifier;
- production key custody, rotation, HSM, keyring integration, or broader
  operational security guarantees;
- production concurrency guarantees for the single-threaded `MemStore`;
- MCP write paths or an ordinary CLI writer;
- librarian or navigator functionality;
- model or lens ingestion;
- knowledge-graph traversal;
- vector retrieval, reranking, or evaluator infrastructure;
- production deployment packaging, public hosting, or a supported service;
- crates.io publication or stable pre-1.0 Rust APIs;
- compatibility with arbitrary future policy versions.

Absence is not architectural rejection unless another doctrine says so. Most
items are possible later work, but none may be inferred from the `v0.1.0`
name.

## 7. Trust model and trusted construction

### What v0.1 proves within its assumptions

Given the caller-supplied verifying key as trust root, the implemented
construction narrowly establishes:

- integrity, order, signatures, and genesis binding of the accepted history;
- deterministic, complete verified replay of one record snapshot;
- exact governed-standing outcomes under the named v0 and v1 policies;
- exact occurrence/inclusion of the one matched v1 five-field proposition;
- reproducible audit traces and the named derived comparison bytes.

### What v0.1 does not prove

The release does not establish:

- that the caller selected the socially correct trust root;
- the truth of arbitrary claims;
- correctness of foreign Deadbolt bundle contents;
- wisdom, safety, desirability, success, or interpretation of anchored actions;
- interpretation truth;
- production security or secure key custody;
- legitimate origin of manually constructed public structs;
- admission of ordinary human or agent claims.

### Sole legitimate trusted origins

- `LogWriter` is the explicit append capability and holds the signing key.
- Successful `LogReader` verification establishes an accepted record snapshot
  relative to the supplied verifying key.
- `LogReader::replay` verifies one snapshot completely and only then folds
  those same events into projections.
- `replay_standing_context` is the legitimate composite construction for
  co-derived standing and anchor context.
- Callers choose the explicit named v0 or snapshot-only v1 resolver; there is
  no ambient latest-policy resolver.

### Manual or adversarial bypasses outside the claim

None of the following establishes trusted resolver provenance or authority:

- caller-created trace, application, or resolution structs;
- independently constructed `StandingView` and `DeadboltAnchorIndex` values;
- two unrelated replay calls treated as shared provenance;
- unverified `LogReader::events()` reads;
- self-asserted actor classes or evidence-kind labels;
- prose, summaries, or content hashes;
- caller-provided `verified`, `admitted`, or `trusted` booleans;
- foreign anchor contents not checked by their native verifier.

## 8. Versioning rules

### Format versioning

- `magpie-core-v1` is a canonical format identity, distinct from crate semver.
- Changing a crate version does not change canonical encoding.
- Changing an existing canonical encoding requires explicit format evolution
  and a new profile; existing bytes remain frozen.
- Additive tags under the same profile must follow `docs/FORMAT.md` evolution
  rules and leave all earlier bytes unchanged.

### Policy versioning

- Policy identity is part of the meaning of every governed resolution.
- Semantic changes to `magpie-claims-standing-v0` or
  `magpie-claims-standing-v1` require a new policy identity, not silent
  mutation.
- An ambient “latest” policy, runtime selector, or negotiation mechanism is
  not part of this contract.
- Callers must choose the explicit v0 or v1 surfaces.

### Rust API versioning

- All crates remain pre-1.0.
- This contract does not promise source compatibility for public Rust APIs.
- Frozen format bytes and policy-ID-pinned semantics are stronger commitments
  than the current Rust type or method shape.

### Repository release versioning

- The intended repository tag is `v0.1.0`.
- The tag has not been created as of this contract's preflight.
- A later packaging/tag action must point `v0.1.0` at a commit satisfying this
  contract.
- No post-tag source or contract edit may retroactively redefine what that tag
  meant.
- crates.io publication is neither required nor promised.

## 9. Release acceptance checklist

A human-controlled later tag process must confirm:

- [ ] `main` is clean and all intended `v0.1.0` changes are merged.
- [ ] No open PR blocks the release boundary.
- [ ] `cargo fmt --all -- --check`
- [ ] `cargo clippy --workspace --all-targets --locked -- -D warnings`
- [ ] `cargo test --workspace --locked`
- [ ] `cargo run --locked --example tour -p magpie-claims`
- [ ] Independent frozen golden-chain verification:

  ```text
  python tools/verify_chain.py crates/magpie-log/testdata/golden-v1.jsonl ea4a6c63e29c520abef5507b132ec5f9954776aebebe7b92421eea691446d22c
  ```

- [ ] Portable Deadbolt-anchor fixture verification:

  ```text
  python tools/verify_chain.py fixtures/deadbolt-anchor-v1/anchor-log.jsonl d04ab232742bb4ab3a1368bd4615e4e6d0224ab71a016baf8520a332c9778737
  ```

- [ ] Frozen canonical fixtures, hashes, signatures, and representative v0/v1
  resolution bytes are unchanged.
- [ ] Policy identifiers remain exactly `magpie-claims-standing-v0` and
  `magpie-claims-standing-v1`.
- [ ] This contract is reviewed against the exact commit to be tagged.
- [ ] A human explicitly creates the tag and any GitHub release.

This checklist does not add `cargo package`, `cargo publish`, or publication
automation. Packaging readiness is a separate decision and PR.

## 10. Future change rules

- Additive capabilities must not retroactively broaden or alter `v0.1.0`
  claims.
- New achieved-standing behaviour requires a new explicit policy version.
- New canonical format behaviour requires explicit format evolution; existing
  bytes stay valid under their original profile.
- New crate versions may change pre-1.0 Rust APIs while retaining old format
  bytes and policy meaning.
- Release-contract errata may clarify wording but may not broaden the
  historical tag's capabilities.
